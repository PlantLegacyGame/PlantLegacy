# AL-01 — Benchmark and six fixed poses

**Status:** implemented 2026-11-15 (P0); client baseline and A/B matrix completed 2026-11-27.

## What changed

- `apps/client/src/dev/benchmark.ts` runs six configurable camera poses and
  reports per-pose `avg / p50 / p95 / p99 / max` frame time, average GPU time,
  triangles and draw calls. Stats are nearest-rank percentiles over the real
  samples, not a single average.
- Warm-up frames after each pose change are discarded, so shader compilation and
  cache misses do not make the first pose look slow.
- Adjacent poses each get their own window; the runner calls back once when the
  last pose ends.
- Poses, warm-up and window length live in `config/dev.json`
  (`benchmark_poses`, `benchmark_warmup_ms`, `benchmark_pose_ms`). The poses are
  camera-relative offsets from the player plant's centroid, so they are
  reproducible on any world seed.
- The Dev Panel's Debug tab has **Benchmark (AL-01)**: Run 6 poses, Log report,
  live status and the last p95. `window.__plantLegacy.benchmark` exposes
  `start()`, `running()` and `report()` in dev builds.
- The runner consumes the same frame numbers the AL-03 band controller uses, so
  a report describes the frame the player actually gets.

## Not yet

- No automatic CI run or stored baseline image set: a run needs a browser and a
  GPU. The report is produced on demand and logged with `console.table`.
- Poses are fixed in world-relative framing; there is no recorded PNG output
  path (a visual review still needs views taken by hand).
- No server tick report in the same run; `dev_log_network` still owns that.

## Verification

`apps/client/src/dev/benchmark.test.ts` (5 tests): percentile ranks, warm-up
discard, a hidden frame discarded while the pose clock advances, finish callback
fires once, default pose set is six distinct poses. `pnpm typecheck`,
`pnpm lint` (0 errors; 8 warnings and 13 infos remain repo-wide),
`pnpm config:validate`, `pnpm docs:check` and the client test suite pass.

## 2026-11-27 scale baseline

### Server STATE/KEYFRAME fanout

Synthetic run of `broadcastPlantStates` with the shipped 1000-plant cap. The
benchmark stubs the socket write and `JSON.stringify`, so it measures the fanout
selection itself, not serialization. `isInRange calls` is the old per-pair test;
the cell-indexed version makes none.

| Players / states | Before (ms) | Before range calls | After, spread cells (ms) | After, all visible (ms) |
|---:|---:|---:|---:|---:|
| 500 | 13.2 | 249,500 | 10.1 | 28.5 |
| 1,000 | 31.0 | 999,000 | 6.9 | 71.0 |
| 2,000 | 63.0 | 1,998,000 | 9.8 | 78.1 |
| 5,000 | 161.9 | 4,995,000 | 18.2 | 147.7 |
| 10,000 | 410.9 | 9,990,000 | 53.3 | 300.6 |

“All visible” is the worst case where every player subscribes to every state:
the remaining work is the 10M visible plant-player pairs the cap permits, not a
second full scan. The shipped world is the spread-cell case. The new
`stateBroadcast.test.ts` also fans out to 10k players without a per-player scan.

Roots are indexed on create, restore and boot, moved on uproot/reroot, removed
on death and refund, and rebuilt after the dev gallery and stress spawn because
those create plants behind `createPlant`'s back. Every removal in `World` goes
through one helper, so a dead id cannot stay in the cell index.

### Client fixed poses

Run in the local preview at 815x656 CSS (1161x934 drawing buffer at pixel ratio
1.425) with the GPU timer available, on the same enrolled machine as the earlier
Iris Xe figures. The pixel ratio was pinned for the whole pass, because the AL-03
band can otherwise change resolution between poses.

**The earlier pass was measuring the idle timer.** It reported 19.5/22.3 ms for
the first two poses and ~122 ms for the last four, and called the latter
"main-thread contention". `config/render.json` sets `idle_drop_timeout_ms` to
30000. After 30 s without input `animate()` switches to a 100 ms timer
(`IDLE_FRAME_INTERVAL_MS`), and `renderFrame` receives that interval as
`deltaTime`. The first two poses ran before the timeout and the last four after
it, so the ~122 ms was the idle cadence, not a frame cost. A later run started
while the page was already idle read ~111 ms at every pose with only 53 samples
per 6 s, which is what exposed it: the benchmark's sample count was the timer's
rate, not the display's.

The benchmark now keeps the live rAF loop for the duration of a run and gives
the runner `frameMs: 0` for a hidden frame. `BenchmarkRunner.tick` already
discards non-positive times, so the pose clock advances without the idle timer
entering the percentiles. `benchmark.test.ts` pins that discard. A run in a
hidden tab therefore records no samples; it needs the tab visible.

| Pose | Samples | p50 frame | p95 frame | Avg GPU | Draw calls |
|---|---:|---:|---:|---:|---:|
| seedling | 199 | 30.0 ms | 31.8 ms | 26.6 ms | 12.1 |
| canopy-from-below | 360 | 16.6 ms | 18.9 ms | 11.9 ms | 11.1 |
| silhouette | 204 | 29.3 ms | 31.4 ms | 25.8 ms | 12.1 |
| golden-hour-wide | 356 | 16.7 ms | 19.0 ms | 13.4 ms | 11.1 |
| root-layer | 147 | 40.7 ms | 43.0 ms | 37.0 ms | 13.1 |
| terrain-panorama | 153 | 39.1 ms | 41.0 ms | 35.5 ms | 12.1 |

The run collected 1,419 samples. The overall p50 (19.8 ms) is not a useful
comparison between runs here: it sits on the boundary between the vsync-bound
poses and the GPU-bound ones, so a small change in the sample mix moves it a lot.
The per-pose rows are the measurement.

### Renderer A/B matrix

Same seed, camera poses and pinned 1.425 pixel ratio; one change at a time, with
a second baseline at the end to measure drift. Only the four GPU-bound poses are
shown; `canopy-from-below` and `golden-hour-wide` sat on the 16.7 ms vsync line
in every configuration (GPU 11.3–13.4 ms), so they cannot show a difference.

p50 frame time, ms:

| Configuration | seedling | silhouette | root-layer | terrain-panorama |
|---|---:|---:|---:|---:|
| baseline, run 1 | 30.0 | 29.3 | 40.7 | 39.1 |
| DOM grain off | 29.3 | 27.9 | 39.2 | 38.1 |
| shadow pass off | 29.7 | 28.0 | 39.0 | 37.9 |
| `MULTISAMPLE` disabled at runtime | 29.7 | 28.4 | 40.0 | 38.7 |
| baseline, run 2 | 29.6 | 27.8 | 38.8 | 37.8 |

Average GPU time, ms:

| Configuration | seedling | silhouette | root-layer | terrain-panorama |
|---|---:|---:|---:|---:|
| baseline, run 1 | 26.6 | 25.8 | 37.0 | 35.5 |
| DOM grain off | 26.4 | 24.8 | 36.2 | 34.9 |
| shadow pass off | 26.4 | 24.7 | 35.5 | 34.5 |
| `MULTISAMPLE` disabled at runtime | 26.4 | 25.1 | 36.5 | 35.0 |
| baseline, run 2 | 26.3 | 24.7 | 35.3 | 34.5 |

- **DOM grain** and the **shadow pass** each move the heavy poses by about 1 ms,
  which is the same size as the 1–2 ms drift between the two baselines. Neither
  explains the old 122 ms, and neither is the dominant render cost in this scene.
- **MSAA cannot be switched at runtime.** `gl.disable(gl.MULTISAMPLE)` leaves the
  drawing buffer at `SAMPLES = 4` and the timings are identical; Chromium reports
  `isEnabled(MULTISAMPLE)` false whether the flag was enabled or disabled. A real
  A/B needs a context created without antialias: a second `WebGLRenderer` at the
  same 1161x934 size and panorama pose (both with the shadow pass off, so only
  AA differs) measured **22.16 ms GPU at 4x vs 12.70 ms at 1x, +9.5 ms (75%)**.
  That is the one renderer toggle with a material cost,
  but it is a context-creation choice; the client hard-codes `antialias: true`
  and `QualityTier.antialiasing` is not wired to it.
- **The WebGPU overlay was not run as an A/B.** `webgpu_enabled` is read at
  startup, the dev panel's "Toggle WebGPU" only receives a server acknowledgement
  (there is no client handler), and enabling the path replaces the plant renderer
  with the WebGPU one. That is a backend comparison, not a same-scene toggle, and
  it needs a restart with a matched scene. It remains for the Phase 6 renderer
  work; it is not part of the 10 fps explanation.
