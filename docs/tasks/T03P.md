# T03P — Networking gate (Gate 0)

**Status:** `[ ]` transport and the 20 Hz authoritative loop work; server-side
rejection is not effective yet, so the Gate 0 acceptance criteria are not fully
met.
**Phase:** 0 — Foundation. **Depends on:** T00.
**Config owner:** `config/net_proto.json`.
**Commits:** `d98adaf` (server, protocol, client), `6a8f5e0` (Vite proxy),
`7d22644` (client WebSocket URL).

## Scope delivered

- WebSocket server at `/ws` with JSON messages `{ type, payload }`.
- `PROTOCOL_VERSION = 1`, `HELLO` version check, `WELCOME`, `STATE`,
  `KEYFRAME`, `REJECT`, `PING` / `PONG`, `ERROR`.
- `CubeWorld`: one cube per player, unique id and color, 20 Hz tick, full
  `KEYFRAME` every `keyframe_interval_ticks`, delta-shaped `STATE` otherwise.
- Client: connects, sends `HELLO`, sends `INPUT` at 20 Hz, renders received cube
  state, reconnects after 3 s on close.
- CORS origin allowlist also gates the WebSocket handshake.
- `config/net_proto.json` populated with 9 values.
- [`docs/protocol.md`](../protocol.md) documents framing, messages, payloads and
  quantization.

## Acceptance evidence

| Criterion | Evidence | Result |
|---|---|---|
| Two tabs, one server, one cube each | Live Pages session: `wss://…/ws` → 101, server log `player joined` with distinct `cubeId`s | pass |
| Unique color per cube | `CubeWorld.addPlayer` assigns a color per player | pass |
| WASD / arrows move the cube | Live browser session; `INPUT` frames sent at 20 Hz | pass |
| Server rejects excess velocity | `speed = 5.0` hardcoded; each input moves 0.25 units/tick, below the 0.5 limit, so the branch never fires | **fail** |
| Server rejects out-of-bounds | `worldBounds.minX` etc. are read, but the config stores `min_x` etc., so the comparison uses `undefined` | **fail** |
| Rejected input → `REJECT` + authoritative state | Code path exists; no current input triggers it | **fail** |
| `KEYFRAME` every 10 ticks, `STATE` otherwise | `step()` checks `tick % keyframeIntervalTicks` | pass |
| Protocol documented | [`docs/protocol.md`](../protocol.md) | pass |

Live bounds probe (2026-11-02): a client sent 4,100 `moveForward` inputs with
increasing tick numbers. The cube reached `z = 1017.734375` and the client
received **0** `REJECT` frames. The expected result was `out_of_bounds` at
`|z| > 1000`.

## Known limitations

- `speed = 5.0` is hardcoded in `apps/server/src/ops/net.ts` (RULE_3 gap). It
  should be a `net_proto` tunable.
- `world_bounds` is stored as snake_case but read as camelCase, so bounds are
  not enforced.
- There are no automated tests for `validateMovement`, quantization or the
  WebSocket message flow.
- No persistence: reconnect creates a new player and cube.
- `STATE` currently sends every cube, not only changed cubes.
- The quick-tunnel origin must be present in `CORS_ORIGINS` or the handshake is
  rejected with code 4001.
