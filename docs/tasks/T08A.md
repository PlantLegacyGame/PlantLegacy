## 1. What exists

- **Item definitions** in `config/items.json`: `item_definitions`,
  `starting_inventory`, `inventory_slots`, and the effect values
  `fertilizer_minerals_gain`, `dung_water_gain`, `dung_minerals_gain`,
  `essence_energy_gain`.
- **Inventory model** in `apps/server/src/ops/inventory.ts`: `createInventory`,
  `addItem` with stack-limit fill then empty-slot placement, and removal.
- **Item config loading and effects** in `apps/server/src/ops/items.ts`.
- **Wire support** (see `docs/protocol.md`): `INVENTORY_REQUEST` (24),
  `INVENTORY_SLOT_USE` (25), `INVENTORY_SLOT_SWAP` (26), `INVENTORY_SYNC` (27),
  `INVENTORY_SLOT_UPDATE` (28). The client receives sync and slot updates.
- **Pouch and purse surfaces (2026-11-20):** the inventory panel and hotbar
  render the server's pouch, the spore chip renders `INVENTORY_SYNC.sporeBalance`,
  and the shop (`ops/shop.ts`, `SHOP_PURCHASE`) spends the purse and grants into
  the same pouch.
- **Restart copy (2026-11-22):** `apps/server/src/ops/persistence/playerStatePersistence.ts`
  reads and writes one `player_state` row per account. `main.ts` loads it before
  a HELLO creates or reclaims a player, writes it after shop purchases, spore
  awards, item use, slot swaps, dev grants and disconnect, and flushes every
  live account on shutdown. The row is the lock; the write is one upsert.
  Guests still have no restart copy, and the write is not yet a full
  read-modify-write transaction.

## 2. Deviation from the spec — read this before building on it

DESIGN T08A requires:

> "Server-authoritative inventory per player per World. Every mutation is a
> transaction with Postgres row-level locking. **No in-memory inventories.**"

What ships instead:

| Requirement | Shipped state |
|---|---|
| Inventory persisted per player in Postgres | **Partial.** `player_state.owner_id` → `slots` and `spores`; account-scoped, not plant-scoped |
| Every mutation row-locked in a transaction | **Partial.** One upsert takes the row lock, but the live `Inventory` is still the object that is mutated; there is no read-modify-write transaction per action |
| Survives restart / reconnect | **Yes for signed-in accounts.** Verified by buying in one session, restarting the server, reconnecting with the same token and reading the same pouch and purse. Guests are session-only |
| Flag validator: `account_bound` ⇒ not tradeable/mailable/listable | **No.** `item_flags.json` is a stub; T08A's acceptance criterion is unmet |
| UI reads, never mutates | Yes for the pouch and purse: the inventory panel, hotbar and spore chip render server messages, and the shop only names an item (`SHOP_PURCHASE`); the server checks the price and grants |

**Consequence.** An account pouch and purse now survive a restart, so the shop
is no longer a pure local slice. It is still not the transaction base the
economy (T14, T45, T29) needs: two sessions cannot mutate one account because
only one active player is allowed, but a future second writer would need the
read-modify-write path. Treat the row as the restart copy, not as the live
inventory.

## 3. Config drift to resolve

The spec names `config/inventory.json` and `config/item_flags.json`; the shipped
code reads `config/items.json`, which is not in the spec or the DESIGN Part 6.2
tree. Resolve deliberately when T08A is completed: either the spec adopts
`items.json` (with an ADR), or the values move into `inventory.json` and
`item_flags.json`. Do not leave three files where the design names two.

## 4. Tests (updated 2026-11-15)

`apps/server/src/ops/inventory.test.ts` (8) covers stack filling, spill into
empty slots, partial fits when full, unknown items, invalid counts (zero,
negative, fractional, NaN), removal across stacks, presence checks, `setSlot`
shape/bounds/stack-limit rejection and swap bounds. `items.test.ts` (3) covers
the RULE_23 invariant (account-bound items cannot be tradeable/mailable/listable)
and rejects non-positive or fractional stack limits at load.

`playerStatePersistence.test.ts` (7) covers slot sanitising (unknown items, bad
counts, stack clamping, short/oversized arrays), conversion round trips, the
no-row case, a `pg` BIGINT read, and the upsert payload. A local database round
trip and an end-to-end buy → restart → reconnect check were run against a
temporary test database on 2026-11-22, and a second live session replacing the
first carried the live pouch rather than the stale row. They are not part of
`pnpm test`, because the suite must not require a live Postgres. The tests prove
the restart copy, **not** a full concurrent transaction.
