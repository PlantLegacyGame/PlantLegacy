# T08A: Inventory

**Status:** `[~]` **partial; the restart copy, locked shop purchase, locked item
use, locked slot swap, locked spore awards and locked dev item grants exist; the
duplication audit does not.** Local inventory behaviour is hardened and tested,
and signed-in accounts load their pouch and purse from `player_state` after a
restart (verified 2026-11-22). A purchase, an item use, a slot swap, a spore
award and a dev item grant each read the row, apply the change and write the
result inside one `SELECT ... FOR UPDATE` transaction, so two clicks cannot
spend the same item or spores and a grant cannot race a purchase. The dev grant
still answers in its own command with the count a grant would add; the sync that
follows the commit carries the committed pouch. Config ownership is resolved
(ADR-082).

it costs.

## 1. What exists

- **Item definitions** in `config/items.json`: `item_definitions`,
  `starting_inventory`, `inventory_slots`, and the effect values
  `fertilizer_minerals_gain`, `dung_water_gain`, `dung_minerals_gain`,
  `essence_energy_gain`.
- **Inventory model** in `apps/server/src/ops/inventory.ts`: `createInventory`,
  `addItem` with stack-limit fill then empty-slot placement, and removal.
- **Item config loading and effects** in `apps/server/src/ops/items.ts`.
- **Wire support** (see `docs/protocol.md`): `INVENTORY_REQUEST` (24),
  `INVENTORY_SLOT_USE` (25), `INVENTORY_SLOT_SWAP` (26), `INVENTORY_SYNC` (27),
  `INVENTORY_SLOT_UPDATE` (28). The client receives sync and slot updates.
- **Pouch and purse surfaces (2026-11-20):** the inventory panel and hotbar
  render the server's pouch, the spore chip renders `INVENTORY_SYNC.sporeBalance`,
  and the shop (`ops/shop.ts`, `SHOP_PURCHASE`) spends the purse and grants into
  the same pouch.
- **Restart copy (2026-11-22):** `apps/server/src/ops/persistence/playerStatePersistence.ts`
  reads and writes one `player_state` row per account. `main.ts` loads it before
  a HELLO creates or reclaims a player, writes it after shop purchases, spore
  awards, item use, slot swaps, dev grants and disconnect, and flushes every
  live account on shutdown. The row is the lock; the write is a transaction that locks it and
  upserts. A shop purchase uses `PlayerStateStore.mutate`, which seeds and locks
  the row, reads the current pouch and purse, applies the purchase there and
  writes the result before commit. Guests still have no restart copy, and item
  use, slot swap and spore awards are not yet on the locked path.

## 2. Deviation from the spec — read this before building on it

DESIGN T08A requires:

> "Server-authoritative inventory per player per World. Every mutation is a
> transaction with Postgres row-level locking. **No in-memory inventories.**"

What ships instead:

| Requirement | Shipped state |
|---|---|
| Inventory persisted per player in Postgres | **Partial.** `player_state.owner_id` → `slots` and `spores`; account-scoped, not plant-scoped |
| Every mutation row-locked in a transaction | **Partial.** A shop purchase, an item use, a slot swap, a spore award and a dev item grant are each one `BEGIN` → seed → `SELECT ... FOR UPDATE` → apply → upsert → `COMMIT` transaction (`PlayerStateStore.mutate`, wired through `InventoryPorts.mutateState`, `World.mutateInventoryState` / `awardSporesLocked` and `ops/itemGrant.ts` for `World.plantCommandPorts.grantItem`). The dev grant's same-command reply is the count a grant would add; the `INVENTORY_SYNC` after the commit carries the pouch the row holds. Nothing else writes the pouch; the duplication audit has not run |
| Survives restart / reconnect | **Yes for signed-in accounts.** Verified by buying in one session, restarting the server, reconnecting with the same token and reading the same pouch and purse. Guests are session-only; a guest reclaim gets an empty pouch and zero spores rather than a fresh starter kit, so reconnecting cannot farm items |
| Flag validator: `account_bound` ⇒ not tradeable/mailable/listable | **Yes at the definition and config boundaries.** `loadItemsConfig` rejects the conflict and the config validator reports it; bundle/listing/mail paths wait for T14/T29/T45 |
| UI reads, never mutates | Yes for the pouch and purse: the inventory panel, hotbar and spore chip render server messages, and the shop only names an item (`SHOP_PURCHASE`); the server checks the price and grants |

**Consequence.** An account pouch and purse survive a restart, and every pouch
and purse mutation this build has — purchase, item use, slot swap, spore award
and dev item grant — cannot double-spend inside one process. It is still not the
transaction base the economy (T14, T45, T29) needs: only one active player is
allowed, and the trade/mail/list systems do not exist. Treat the row as the
restart copy and these locked writes as a slice, not a finished economy.

## 3. Config ownership — resolved

`config/items.json` is the single catalogue for definitions, flags, stack
limits, starting inventory and slot count (ADR-082). DESIGN T08A now names it.
`config/inventory.json` and `config/item_flags.json` are marked `deprecated`, keep
empty values and have no readers. The RULE_23 invariant is enforced in
`loadItemsConfig` and by the config validator.

## 4. Tests (updated 2026-11-22)

`apps/server/src/ops/inventory.test.ts` (8) covers stack filling, spill into
empty slots, partial fits when full, unknown items, invalid counts (zero,
negative, fractional, NaN), removal across stacks, presence checks, `setSlot`
shape/bounds/stack-limit rejection and swap bounds. `items.test.ts` (3) covers
the RULE_23 invariant (account-bound items cannot be tradeable/mailable/listable)
and rejects non-positive or fractional stack limits at load.

`playerStatePersistence.test.ts` (11) covers slot sanitising (unknown items, bad
counts, stack clamping, short/oversized arrays), conversion round trips, the
no-row case, a `pg` BIGINT read, the upsert payload, the lock order,
read-modify-write inside the lock, a refused mutation rolling back without a
write, write serialisation per owner, and rollback/release on failure. A local database round
trip and an end-to-end buy → restart → reconnect check were run against a
temporary test database on 2026-11-22, and a second live session replacing the
first carried the live pouch rather than the stale row. A two-concurrent-purchase audit sent two
80-spore purchases against a 120-spore purse: exactly one succeeded, the other
answered `insufficient_spores`, and a restart still showed 40 spores and one
item. They are not part of `pnpm test`, because the suite must not require a live
Postgres. The audit proves the purchase path, not every mutation.

`inventoryHandlers.test.ts` (11) now also pins the locked path: the slot is
spent in the stored state before the plant effect is applied, and a use whose
item another click already spent is refused with no effect and a re-sync.

`playerStateMutations.ts` holds the path the world and the audit share:
`mutatePlayerState` (locked row, or the live plan when there is none) and
`awardSporesStored`. Its rule is that the caller adopts the state **as
committed**, not its own plan: `PlayerStateStore.mutate` calls `onCommitted`
with the sanitised values it wrote, after `COMMIT`, so a plan clamped on the way
in (a stack above its limit, a purse above the maximum) cannot leave the live
pouch ahead of the row. `World.purchaseShopItem`, `World.mutateInventoryState`
and `World.awardSporesLocked` all adopt through that callback.
`playerStateMutations.test.ts` (4) covers the guest plan, the clamped adoption
and the refused change; `playerStatePersistence.test.ts` (14) pins that the
callback runs after `COMMIT` with the sanitised state, never for a refusal, and
that a hook which throws is reported to the repair sink and swallowed instead of
failing a write that already committed. `shopPurchase.test.ts` (2) drives the
purchase composition (`ops/shopPurchase.ts`, which `World.purchaseShopItem`
calls) through a store that commits a clamped row: the plan is 70 spores and one
item, and the live player must adopt the row's 1000 spores and full stack rather
than the plan; a refusal adopts nothing. `itemGrant.test.ts` (4) covers the
locked dev grant: the preview counts without writing, a grant adopts the pouch
the row committed (three added to a row that already held two reads back as
five), a full locked pouch adds nothing and adopts nothing, and a guest falls
back to the live pouch. `dev/plantCommands.test.ts` pins that the command still
answers in the same call with the count a grant would add.

## 5. What would close T08A

1. **Done:** `player_state`, `PlayerStateStore`, load on HELLO, write-back on the
   mutation paths, and locked read-modify-write paths for purchases, item use,
   slot swap and spore awards. The plant's resource gain from an item is applied
   after the row commits, so a refused change cannot leave a free handful of
   minerals behind. Dev item grants go through the same locked mutation
   (`ops/itemGrant.ts`); their command still answers in the same call with the
   planned count, and the sync after the commit carries the committed pouch.

3. **Done:** `items.json` is the single catalogue; the two named files are deprecated stubs (ADR-082).
4. Slot selection UI (C04/C05).
5. **Done:** unit tests for the store, the row-lock order, the committed-state
   adoption and rollback, plus a local database round trip, a buy → restart →
   reconnect check, a live session replacement and the formal two-concurrent-
   purchase audit (one success, one `insufficient_spores`, durable 40/1 after
   restart). The item-use and award paths were audited against the compose
