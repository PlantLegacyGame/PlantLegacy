# AL-03 — GPU-band quality controller

**Status:** implemented 2026-11-15 (P0).

## What changed

- `apps/client/src/render/GpuTimer.ts` reads real GPU frame time from
  `EXT_disjoint_timer_query_webgl2`. It degrades to a null timer when the
  driver does not expose the extension or reports a disjoint result, so the
  game never depends on it.
- `QualityController` now runs a closed loop over measured cost
  (`gpuBandMinMs` / `gpuBandMaxMs`) instead of comparing vsync-clamped CPU fps
  with a target. Over budget it spends detail in a fixed order:
  **resolution → draw distance → tier**. Under budget it recovers in the
  reverse order, one lever at a time, after `qualityHoldMs`.
- A triangle overflow is treated as a hard budget: the tier drops immediately
  and the finer levers reset, because lowering resolution cannot fix too many
  triangles.
- Draw distance is a real lever, not a readout: `WebGPURenderer.setLodThresholdScale`
  multiplies the projected-size tier thresholds, so a tighter band promotes
  plants to cheaper tiers sooner.
- New tunables in `config/render.json`: `gpu_band_min_ms`, `gpu_band_max_ms`,
  `quality_hold_ms`, `draw_distance_floor`.

## Follow-up (2026-11-15): the resolution lever was inert

`config/render.json` shipped `resolution_floor: 1.0` and `max_pixel_ratio: 1`,
so `pixelScale` could never leave 1 and the first lever of the band was a
no-op. Fixed:

- `resolution_floor` 0.5, `max_pixel_ratio` 2.0, so the lever has room in both
  directions.
- The lever bounds are now relative to the tier's own pixel ratio
  (`floor / tierBase`, `ceiling / tierBase`), so a high tier cannot be pushed
  past the configured ceiling by multiplying a larger base.
- Estimated (CPU) timing no longer uses the pixel band. A 60 Hz device clamped
  by vsync sits at 16.7 ms with unknown headroom, which a pixel band would read
  as over budget and degrade forever. Estimated mode degrades only below the
  configured warning fraction of target fps, recovers toward native (never
  above 1.0), and never promotes a tier on vsync alone.
- `apps/client/src/render/renderConfig.test.ts` guards the shipped values, so a
  config edit that collapses the lever fails in CI instead of in a browser.

## Follow-up 3 (2026-11-15): warm-up and smoothed input

Two problems were left by follow-up 2: the session opened at `0.5` because the
band acted on shader-compile and upload frames, and a single hitch spent a
resolution step. Both are fixed in the controller:

- `quality_warmup_ms` (default 4000): cost is still smoothed during warm-up but
  no lever moves, and the over-budget window is cleared, so warm-up cannot be
  inherited by the first real decision.
- `quality_smoothing` (default 0.12): the band decides on an exponential moving
  average of cost, not the latest frame.
- Spending now requires the smoothed cost to stay over budget for a whole
  `quality_hold_ms` window (`overBudgetSinceMs`) **and** the hold to have
  elapsed since the last change. Previously only recovery respected the hold,
  which is why one frame could drop resolution. Triangle overflow is still
  immediate: it is a hard budget, not a cost blip.

Tests cover each: load spikes during warm-up change nothing, one 240 ms frame
against steady 16.7 ms frames changes nothing, and sustained over-budget frames
still spend detail after the hold.

## Follow-up 2 (2026-11-15): estimated recovery capped at native

The first fix capped the recovery *scale* at 1.0, but the scale multiplies the
*tier's base ratio*, so a medium tier (base 1.25) still recovered to 1.25 and
the ratio sawtoothed between about 0.94 and 1.25 — above native, then a degrade,
then back up.

- `effectivePixelRatio(state, config)` is now the only place the ratio is
  computed, and it caps the ceiling at native (`1.0`) until a **real GPU sample**
  has been seen. `state.gpuTimingSeen` latches on and never turns off, so a
  driver that reports timer queries regains the full config range.
- The recovery ceiling is expressed relative to the tier base
  (`min(config.maxPixelRatio, 1) / tierBase`), and the state is clamped to it
  whenever it drops.
- Tests assert the cap on every tier and that a measured sample may still use
  the full range; the comment now matches what the code does.

Observed in the browser after the change: the ratio stayed at or below `1.0`
for a 10 s sample (previously it crossed to 1.25), climbing from `0.5` on load
to `1.0`. It still dips a step under real hitches, because a single over-budget
sample spends detail; smoothing the band input is a separate change.

## Browser findings (2026-11-15)

- The first implementation called `ext.beginQueryEXT` / `ext.endQueryEXT`. In a
  WebGL2 context Chromium exposes the query functions on the **context**
  (`gl.beginQuery` / `gl.endQuery` / `gl.getQueryParameter`) and the extension
  only adds `TIME_ELAPSED_EXT` / `GPU_DISJOINT_EXT`. The timer now resolves the
  working shape once, supports both, and never throws into the frame loop.
- A query may only be read after it has been ended. The timer tracks an
  `active` flag; polling a running query was raising
  `INVALID_OPERATION: getQueryParameter: query is currently active` every frame.
- On this machine the extension is present and the calls are valid, but no
  usable GPU sample was ever reported (`gpuMeasured: false` after a full
  six-pose run), so the band ran on CPU frame time. The fallback path is the
  documented one; whether this driver simply reports disjoint every frame is
  unproven.

## Not yet

- No `EXT_disjoint_timer_query` (WebGL1) fallback; the client is WebGL2.
- No per-device persistence of the chosen settings yet, and no device-loss
  reset of the controller state.
- Post/shaft toggles are not in the lever chain because there is no post chain
  yet (AL-04).
